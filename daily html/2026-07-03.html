Microsoft 成立“Frontier Company”，斥资 25 亿美元派驻 6000 名 AI 工程师到企业客户现场

Microsoft 新设业务部门“Frontier Company”，拨款 25 亿美元，将 6000 名行业与工程专家派驻企业客户现场，“共同设计、共同创新、部署并持续改进 AI 系统”。该部门由 Rodrigo Kede Lima 领导，旨在超越“前部署工程”模式，成为“最大、以结果为导向的工程组织”。Microsoft 将自己定位为 OpenAI 和 Anthropic 的“平台中立”替代方案，后两者也已设立专门部署公司。Microsoft 将借助埃森哲、凯捷、安永等系统集成商扩大覆盖范围。

AI PM 视角：Microsoft Frontier Company 的成立标志着企业 AI 服务从“卖 API 和许可证”正式转向“卖结果和共同交付”。过去两年，大模型厂商的核心竞争点是模型能力和价格，但企业客户真正的痛点并非模型不够强，而是不知道如何将模型嵌入复杂业务流程、如何保证合规与安全、如何衡量 ROI。Frontier Company 用 6000 名驻场工程师和 25 亿美元预算，直接把微软服务团队嵌入客户组织，本质上是在销售“AI 转型结果”而非“AI 工具”。 从产品竞争格局看，Microsoft 此举是对 OpenAI、Anthropic 以及 Google 的正面防御。OpenAI 已成立专门服务企业部署的团队，Anthropic 也在扩大企业解决方案，Google 则通过 Cloud 咨询服务覆盖大客户。Microsoft 的优势在于 Azure、M365、Dynamics 和 GitHub 已经深度嵌入企业 IT 架构，驻场工程师可以无缝调用这些工具链。但“平台中立”定位是一把双刃剑：一方面可以安抚担心被 OpenAI 锁定的客户，另一方面也可能稀释 Microsoft 与 OpenAI 的独家合作优势。 对 AI PM 的关键启示是：企业 AI 产品的下一个竞争焦点不是模型榜单，而是“最后一公里交付能力”。客户愿意为确定性的业务结果付费，而不是为不确定的模型性能买单。Frontier Company 的模式也可能重塑 SaaS 行业的客户成功组织——从远程支持转向驻场共创，从培训客户转向直接替客户跑通业务闭环。

研究型 Builder 视角：技术层面，Frontier Company 揭示了一个被低估的趋势：企业 AI 的核心瓶颈正在从模型能力转向“系统集成、数据治理和变更管理”。6000 名工程师派驻客户现场，意味着 Microsoft 承认再强的通用模型也无法直接适配每个企业的遗留系统、数据孤岛和合规要求。研究型 Builder 应关注这类大规模驻场交付中沉淀出的可复用组件、参考架构和行业模板，它们很可能成为下一代企业 AI 中间件的基础。同时，这也验证了“AI 工程 > 模型研究”在企业落地阶段的优先级。

可落地的方法论：- **本周可做**：梳理你所在企业或产品的 TOP 3 高价值业务场景，评估是否需要引入外部驻场工程团队或建立内部“AI 交付突击队”，将模型能力转化为可量化的业务指标。 - **本季度可做**：如果你是 ToB AI 产品负责人，设计一套“结果导向”的定价或成功指标体系，将客户付费与客户业务 KPI 改善挂钩，而非按 token 或座位数计费。 ---

AI 版支付宝开放公测，蚂蚁阿宝无需邀请码即可体验

支付宝阿宝 AI 助手今日正式开放公测，iOS 和安卓用户可在应用商店或支付宝 App 搜索“阿宝”或“蚂蚁阿宝”直接体验。开通后右滑进入新版，以对话方式安排办事，例如说出“查公积金”，阿宝会自动匹配对应小程序和服务入口，用户点击确认即可完成。支付宝承诺所有资金变动与支付环节均需用户本人确认，扫码、转账等功能已预留入口。

AI PM 视角：支付宝阿宝的开放公测是中国超级 App AI 化的标志性事件。与独立的 AI 助手不同，阿宝直接生长在拥有 10 亿用户的支付和生活服务平台上，天然掌握用户身份、支付能力、小程序生态和本地服务图谱。这意味着它不需要从零建立用户信任或使用习惯，而是把 AI 对话层叠加在已有高频行为之上。对 AI PM 来说，这是“入口即生态”的典型案例：模型不是产品，模型+场景+信任+支付闭环才是。 从产品设计角度看，阿宝选择了“对话编排 + 人工确认”的安全路径。所有资金变动都需要用户本人确认，这既是对金融场景合规性的尊重，也降低了用户对 AI 自动执行敏感操作的抵触。相比之下，一些追求全自动的 Agent 产品可能在非金融场景更激进，但在支付、转账、政务办事等高风险场景中，可控性和可解释性是比效率更优先的 UX 原则。阿宝的右滑入口、自然语言调用小程序、服务自动匹配，实际上是在重新定义超级 App 的导航结构——从“搜索-点击-填写”的表单逻辑，转向“说出意图-AI 匹配-用户确认”的对话逻辑。 更深层的竞争意义在于，阿宝可能成为蚂蚁集团对抗微信、抖音等超级 App AI 化的核心武器。微信有社交关系链，抖音有内容推荐引擎，而支付宝的核心壁垒是交易和服务闭环。如果阿宝能真正打通公积金、社保、医保、出行、缴费等政务民生服务，它将成为中国用户办理“麻烦事”的首选入口，而不仅仅是支付工具。

研究型 Builder 视角：技术上，阿宝的核心挑战不是对话生成，而是“意图理解 -> 服务路由 -> 表单预填 -> 支付确认”的全链路可靠性。它需要解决多轮对话中的指代消解、小程序 API 的动态调用、用户身份与权限的安全传递等问题。研究型 Builder 应关注蚂蚁是否会开源其服务编排框架或 Agent 协议，因为这代表了中文语境下超级 App AI 化的工程范式。同时，这也是一个观察“LLM + 结构化工具调用 + 人类在环”如何在亿级用户产品中落地的重要窗口。

可落地的方法论：- **本周可做**：如果你是超级 App 或平台型产品负责人，绘制你的产品服务图谱，识别哪些高频、多步骤、规则明确的操作可以被自然语言意图入口替代。 - **本季度可做**：设计一个“AI 办事助手”的最小可用场景，重点不是让 AI 完成所有操作，而是让 AI 准确找到服务入口并预填信息，最后一步由用户确认执行。 ---

阿里巴巴发布 Page Agent：开源 JavaScript 库实现网页 DOM 自然语言操控

阿里巴巴发布 Page Agent，一个开源的 JavaScript 客户端库，嵌入网页后可通过自然语言指令直接操作 DOM 元素。与 Playwright、Puppeteer 等外部浏览器自动化工具不同，Page Agent 不依赖截图或多模态模型，而是将实时 DOM 脱水压缩为 FlatDomTree 文本映射，让纯文本模型精准执行点击、表单填写等操作。它继承用户 cookies 和会话，无需独立后端，并支持任意 OpenAI 兼容端点的模型（示例使用 qwen3.5-plus）。项目采用 MIT 许可证，适合在自有应用内构建 AI 副驾、智能表单填充或无障碍控制等场景，但限于单页面范围，风险操作仍需服务端验证。

AI PM 视角：Page Agent 代表了一种与当前主流“浏览器自动化 Agent”完全不同的技术路线。市面上的 Web Agent（如基于 Playwright 的方案）大多依赖截图 + 多模态模型来理解页面并执行操作，成本高、延迟大、对动态页面和隐私内容的处理能力有限。Page Agent 则反其道而行：它直接运行在页面内部，把 DOM 结构压缩成纯文本表示，让文本模型就能精准操作。这种“内嵌式 Agent”架构在成本、延迟、隐私和可解释性上都有明显优势。 对 AI PM 来说，Page Agent 的最大价值在于它为企业提供了一种在自有产品内构建 AI 副驾的低门槛方案。用户不需要安装浏览器插件或外部自动化工具，只需在产品前端引入一个 JS 库，就能让 AI 理解当前页面、帮助用户填写表单、导航功能、完成复杂操作。这比“做一个新的 AI 原生应用”更容易落地，因为它不改变用户现有的使用习惯，而是增强现有界面。对于 B2B SaaS、政务系统、金融服务等复杂表单密集型产品，Page Agent 可能是比重新设计对话式 UI 更务实的 AI 化路径。 不过，Page Agent 也有明显边界：它限于单页面范围，无法跨页面导航，风险操作仍需服务端验证。这意味着它更适合作为“页面内智能助手”，而非完整的跨应用自动化 Agent。产品设计时需要明确它的能力边界，避免用户产生“AI 可以替我完成一切”的错误预期。

研究型 Builder 视角：技术层面，FlatDomTree 的设计是 Page Agent 的核心创新。它将动态 DOM 脱水压缩为文本映射，让纯文本模型无需多模态能力就能理解页面结构和元素语义。这种方法在延迟和成本上优于视觉方案，但研究型 Builder 需要关注几个关键问题：压缩后的 DOM 表示是否会丢失关键语义信息？动态加载内容（如懒加载、Shadow DOM、Canvas 渲染）如何处理？模型对 FlatDomTree 的泛化能力在不同网站结构间是否稳定？这些问题的答案将决定 Page Agent 是否能在复杂真实场景中大规模复用。

可落地的方法论：- **本周可做**：在你的 Web 产品中选取一个复杂表单或配置页面，试用 Page Agent 或类似 DOM 感知方案，测试 AI 能否准确理解字段含义并辅助用户填写。 - **本季度可做**：构建一个“页面内 AI 副驾”的 MVP，优先覆盖新用户引导、复杂配置助手或无障碍辅助场景，收集用户对“AI 直接操作界面”的信任度和接受度数据。 ---

Fable 5 在 RLI 基准中达成 16.1% 自动化率，较八个月前提升六倍

Remote Labor Index（RLI）衡量 AI 智能体完成 240 个付费自由职业项目（总值 14.4 万美元）的专业质量比例。最新结果显示，Fable 5 自动化率达 16.1%，是八个月前最佳系统 2.5% 的六倍多，也超过 Opus 4.8（8.3%）和 GPT-5.5（6.3%）。因美国政府限制访问，Fable 5 仅完成 218/240 个项目评估，最坏情况仍达 14.6%。Gemini 3 Pro 仅 1.25%，落后于更老模型。AI 裁判会高估模型表现（GPT-5.5 评分偏高近三倍），仍需人类评估员打开专业软件（如 Blender）检验几何模型等细节。测试环境为虚拟 Linux 机，配备 30 余款专业应用。

AI PM 视角：Fable 5 在 RLI 基准上从 2.5% 跃升至 16.1%，意味着 AI 智能体在专业自由职业市场中的可替代边界正在快速外扩。RLI 不同于传统代码基准，它测试的是真实世界中的复杂任务：需要打开专业软件、理解客户需求、交付可被验收的成果。16.1% 的自动化率虽然还不高，但八个月六倍的增长速度表明，AI 替代远程知识工作的趋势正在从“未来叙事”变为“可量化的市场力量”。 对 AI PM 来说，这一事件的核心信号是：Agent 产品的市场定位正在从“辅助工具”向“自主执行者”演进。Fable 5 能够完成的专业任务包括设计、编程、数据分析、内容创作等多个领域，这意味着未来“AI 自由职业平台”或“AI 外包市场”可能成为新的产品形态。企业不再只是购买 AI 工具提升内部效率，而是可以直接购买 AI 完成的交付物。这将冲击 Upwork、Fiverr 等自由职业平台，也会改变企业内部对“可外包任务”的定义。 但 RLI 的结果也提醒我们保持冷静：AI 裁判会显著高估模型表现，说明自动化评估在复杂创造性任务上仍不可靠；Gemini 3 Pro 表现异常落后，说明模型能力并不总是随版本号线性提升；美国政府限制导致 Fable 5 无法完成全部评估，也揭示了地缘政治对 AI 能力评估的干扰。产品设计时，不能只看自动化率数字，还需要建立人类验收闭环和专业领域评估标准。

研究型 Builder 视角：技术层面，Fable 5 在 RLI 上的领先表明，在开放任务环境中，智能体的“规划能力、工具使用广度和错误恢复能力”比单一任务的准确率更重要。RLI 的 240 个项目覆盖 30 多款专业应用，要求智能体不仅要会写代码，还要会操作 Blender、Excel、Photoshop 等工具。研究型 Builder 应关注 Fable 5 的架构设计：它是如何在长周期任务中保持上下文的？如何处理客户需求的模糊性和验收标准？AI 裁判与人类评估的巨大差距也提示我们，复杂任务的自动评估仍是一个开放研究问题。

可落地的方法论：- **本周可做**：列出你所在团队当前外包给自由职业者或外部供应商的任务清单，评估其中哪些可以用现有 Agent 工具初步自动化，优先选择交付标准明确、可验收的任务做试点。 - **本季度可做**：如果你是一个平台型产品负责人，探索在平台内引入“AI 自由职业者”角色，设计任务发布、AI 执行、人类验收和争议仲裁的完整流程。 ---

花旗、Adobe等企业限制员工使用AI旗舰模型以控制成本

据404 Media获取的内部资料，Atlassian、Adobe、亚马逊等六家企业正限制员工使用AI工具，要求改用能力较低的大模型避免成本失控。至少一家企业月度AI开销增至三倍，超1500万美元。花旗银行因GitHub改为按量计费，于6月24日禁用Claude Opus 4.6、4.7及GPT-5.5等旗舰模型。Adobe于6月30日终止Claude无限制使用协议。Atlassian数据显示其AI月支出从500万美元飙升至1500万美元，本财年预计超1.2亿美元。GitHub计划改用开源模型并测试单人按量计费模式。

AI PM 视角：这是 2026 年企业 AI 采用的“成本觉醒”时刻。过去两年，企业为了快速验证 AI 价值，普遍对员工使用旗舰模型采取宽松甚至无限制政策。但当 Atlassian 的月度 AI 支出从 500 万美元飙升至 1500 万美元，当 GitHub Copilot 从固定订阅转向按量计费，当 Adobe 终止 Claude 无限制使用协议，企业开始意识到：AI 的能力红利如果不能与成本结构匹配，就会变成利润黑洞。 对 AI PM 的启示是深远的。首先，AI 产品的定价模型正在从“按座位订阅”向“按用量计费”转移，这要求产品经理重新设计成本控制机制。Claude Enterprise 今日同时推出用量分析和支出限额功能，正是对这一趋势的回应。其次，企业客户会越来越挑剔：他们不再愿意为每个员工都配备最强模型，而是会根据任务复杂度分配模型层级——简单任务用轻量模型，复杂任务才调用旗舰模型。这意味着 AI 产品需要内置“模型路由”能力，自动为用户匹配性价比最优的模型。 从竞争格局看，这一趋势利好开源模型和模型路由中间件。Kimi K2.7 Code 进入 GitHub Copilot，正是因为开源权重模型可以提供更低成本的选择。GitHub 计划改用开源模型并测试单人按量计费，也预示着未来企业 AI 工具的核心竞争力将从“模型是否最强”转向“在同等成本下能否完成更多任务”。

研究型 Builder 视角：技术层面，企业成本管控需求将推动“模型路由、推理优化和成本可观测性”成为 AI 工程的核心方向。研究型 Builder 应关注如何根据任务复杂度、延迟要求和成本预算动态选择模型，以及如何通过 prompt 压缩、缓存、 speculative decoding 等技术降低推理成本。Atlassian 等企业的成本曲线也表明，如果没有用量治理，即使是固定订阅产品也会在按量计费转型中迅速失控。这是一个典型的“规模不经济”问题，需要系统层面的优化而不仅仅是换用更便宜的模型。

可落地的方法论：- **本周可做**：盘点你团队或产品中各场景的 AI 模型使用情况，按任务复杂度分层：哪些任务可以用开源/轻量模型替代旗舰模型？哪些任务必须保留最强模型？ - **本季度可做**：建立 AI 成本治理框架，包括用量监控、模型路由策略、预算告警和 ROI 评估机制，将 AI 支出与业务产出挂钩。 ---

阿里巴巴发布 Page Agent：开源 JavaScript 库实现网页 DOM 自然语言操控

AI PM 视角：Page Agent 代表了一种与当前主流“浏览器自动化 Agent”完全不同的技术路线。市面上的 Web Agent（如基于 Playwright 的方案）大多依赖截图 + 多模态模型来理解页面并执行操作，成本高、延迟大、对动态页面和隐私内容的处理能力有限。Page Agent 则反其道而行：它直接运行在页面内部，把 DOM 结构压缩成纯文本表示，让文本模型就能精准操作。这种“内嵌式 Agent”架构在成本、延迟、隐私和可解释性上都有明显优势。

对 AI PM 来说，Page Agent 的最大价值在于它为企业提供了一种在自有产品内构建 AI 副驾的低门槛方案。用户不需要安装浏览器插件或外部自动化工具，只需在产品前端引入一个 JS 库，就能让 AI 理解当前页面、帮助用户填写表单、导航功能、完成复杂操作。这比“做一个新的 AI 原生应用”更容易落地，因为它不改变用户现有的使用习惯，而是增强现有界面。对于 B2B SaaS、政务系统、金融服务等复杂表单密集型产品，Page Agent 可能是比重新设计对话式 UI 更务实的 AI 化路径。

不过，Page Agent 也有明显边界：它限于单页面范围，无法跨页面导航，风险操作仍需服务端验证。这意味着它更适合作为“页面内智能助手”，而非完整的跨应用自动化 Agent。产品设计时需要明确它的能力边界，避免用户产生“AI 可以替我完成一切”的错误预期。

研究型 Builder 视角：技术层面，FlatDomTree 的设计是 Page Agent 的核心创新。它将动态 DOM 脱水压缩为文本映射，让纯文本模型无需多模态能力就能理解页面结构和元素语义。这种方法在延迟和成本上优于视觉方案，但研究型 Builder 需要关注几个关键问题：压缩后的 DOM 表示是否会丢失关键语义信息？动态加载内容（如懒加载、Shadow DOM、Canvas 渲染）如何处理？模型对 FlatDomTree 的泛化能力在不同网站结构间是否稳定？这些问题的答案将决定 Page Agent 是否能在复杂真实场景中大规模复用。

方法论
  • 本周可做：在你的 Web 产品中选取一个复杂表单或配置页面，试用 Page Agent 或类似 DOM 感知方案，测试 AI 能否准确理解字段含义并辅助用户填写。
  • 本季度可做：构建一个“页面内 AI 副驾”的 MVP，优先覆盖新用户引导、复杂配置助手或无障碍辅助场景，收集用户对“AI 直接操作界面”的信任度和接受度数据。

3 CROSS-CUTTING MODELS
01

框架1：企业 AI 的“交付模式”迁移——从卖工具到卖结果

今天的多个事件共同指向一个结构性转变：企业 AI 市场正在从“卖 API 和许可证”转向“卖结果和共同交付”。Microsoft Frontier Company 用 6000 名驻场工程师直接帮客户落地 AI；Anthropic 与五角大楼的冲突说明政府客户需要供应商具备交付确定性的国家安全能力；花旗、Adobe 等企业限制旗舰模型使用，则反映企业客户开始要求 AI 投入必须产生可衡量的业务回报。

  • 因果链：企业客户对 AI 的兴奋度下降 → 采购决策更理性 → 供应商必须证明 ROI → 驻场共创、结果定价和成本治理成为竞争壁垒。
  • 结构洞察：未来企业 AI 市场的赢家不一定是模型最强的公司，而是最能将模型能力封装为可交付业务结果的公司。

产品启示：AI PM 在设计 ToB 产品时，应尽早定义“业务结果指标”而非“模型性能指标”。例如，不要只汇报代码生成准确率，而要汇报开发周期缩短比例、客服处理量提升或合规成本下降。同时，产品应内置成本治理和用量分析功能，帮助客户证明和控制 AI 投入。

02

框架2：Agent 入口的“嵌入性”原则——用户在哪，Agent 就在哪

支付宝阿宝、Skywork Tags、Page Agent 代表了三种不同的 Agent 嵌入策略：阿宝嵌入超级 App 的服务生态，Skywork Tags 嵌入 IM 群聊协作流，Page Agent 嵌入网页内部作为页面级副驾。三者的共同点是：不创建新的应用入口，而是增强用户已有的高频场景。

  • 因果链：独立 AI 应用获客成本高、留存难 → Agent 主动进入用户已有工作流 → 降低迁移成本 → 通过积累场景上下文提升能力。
  • 结构洞察：Agent 的竞争力不仅来自模型能力，更来自它所嵌入场景的上下文深度和交互频率。

产品启示：在设计 Agent 产品时，优先选择用户已经停留的地方作为入口，而不是新建一个独立平台。对于 B2B 产品，这意味着嵌入 Slack、飞书、钉钉、Salesforce、Office 365 等现有工具；对于 C 端产品，这意味着嵌入超级 App 或浏览器。入口选择决定了 Agent 能获取多少上下文，而上下文决定了 Agent 的实际效用。

03

框架3：AI 成本曲线的“分层治理”——模型不是越贵越好

花旗、Adobe、Atlassian 限制旗舰模型使用，GitHub 引入 Kimi K2.7 Code 开源模型，Runway 通过 deckard 优化 GPU 利用率，Google 用电增长 37%——这些事件共同勾勒出 AI 成本治理的紧迫性。企业开始意识到，无限制使用最强模型在经济和环境上都不可持续。

  • 因果链：旗舰模型成本飙升 + 按量计费普及 → 企业要求按任务复杂度匹配模型 → 模型路由、开源替代和推理优化成为刚需。
  • 结构洞察：AI 系统的经济性取决于“在正确的时间用正确的模型做正确的事”，而非“在所有时间用最强的模型”。

产品启示：AI 产品应内置智能模型路由能力：简单任务用轻量/开源模型，复杂任务调用旗舰模型，批处理任务调度到低成本时段。同时，产品经理需要将能耗和碳足迹纳入模型选型和架构设计考量，以应对未来可能的 ESG 合规要求。
