1 Apple 起诉 OpenAI 窃取商业机密

Apple 于 2026-07-10 向加州北区联邦法院起诉 OpenAI，指控其通过前 Apple 高层 Tang Tan 及前高级系统电气工程师 Chang Liu 等人在招聘过程中窃取未发布产品代号、硬件组件及专有金属精加工技术等商业机密，并要求禁止 OpenAI 使用或披露这些信息、归还相关材料。

AI PM 视角：这起诉讼是 AI 产业从“技术竞速”转向“资产保护”的重要标志。Apple 的指控并不只是普通的员工跳槽纠纷，而是把 OpenAI 描绘成一个系统性利用招聘流程获取机密硬件信息的对手。对于 AI 产品经理而言，这意味着前沿竞争的战场正在扩大：模型能力、数据、算力之外，**硬件工艺 know-how、项目管理和供应链机密**也变成了高价值攻击目标。Apple 要求法院禁止 OpenAI 使用或披露这些信息，实质上是在用法律手段延缓 OpenAI 的硬件化进程。未来产品团队在做竞品分析、人才引进、合作伙伴尽调时，必须把“信息来源合规性”纳入设计阶段，而不是等到法务介入才补救。 从行业格局看，这起诉讼也映射出 AI 公司垂直整合的焦虑。OpenAI 如果要做自有硬件（芯片、终端、机器人），绕不开精密制造与材料工艺；而 Apple 拥有全球最封闭的硬件供应链之一。双方的冲突本质是“模型公司向上游硬件延伸”与“硬件巨头向下游 AI 服务反击”的交汇点。PM 在规划跨领域产品路线时，应把专利、商业秘密、供应链独家协议当作和模型权重同等重要的护城河。

AI Builder 视角：对工程团队来说，这起案件最直接的启示是：AI 项目的保密半径必须扩大。传统上开发者关注代码、模型权重、训练数据；但现在项目代号、硬件样品、内部文档流转路径、面试流程中的信息披露都可能成为泄露点。Builder 需要在 CI/CD、文档权限、招聘面试指引、离职资产回收等环节加入更细的审计与最小权限原则。特别是当团队与外部候选人、供应商、合作伙伴交流时，应建立“可披露信息白名单”，避免在 demo 和面试中无意间暴露关键技术参数。

研究型 Builder 视角：这更像是一起关于“知识如何合法迁移”的边界案例，而非纯技术突破。研究者关心的是：OpenAI 的硬件能力曲线是否真能从这些机密中获得非线性提升？专有金属精加工技术与 AI 硬件散热、封装、结构件之间的关联度如何？此案若进入证据开示阶段，可能会首次披露前沿 AI 硬件公司的内部研发节奏和人才流动模式，对理解 AI 产业创新来源具有社会学与战略研究价值。产品团队可借此案例建立“知识迁移合规审计”机制，把研究成果从法庭文件转化为内部培训素材。

可落地的方法论：- **本周**：在团队招聘 SOP 中加入“候选人信息披露清单”，明确面试中禁止展示的硬件样品、项目代号、内部文档类型。 - **本季度**：对现有 AI 项目进行“商业秘密风险评估”，划分代码、数据、模型、硬件工艺、供应链信息的保护等级，并映射到访问控制与审计策略。 - **长期**：把“合规获取竞品信息”纳入产品经理核心能力模型，避免因为竞速而导致整个产品线陷入诉讼冻结。 ---

2 宇树 G1 人形机器人完成首例活体微创手术

发表于《自然》的研究显示，加州大学圣地亚哥团队使用宇树 G1 人形机器人，以常规手术器械完成两只活猪的腹腔镜胆囊切除术，第二次手术耗时 32 分钟；机器人成本可能仅为达芬奇系统的约 5%，但仍需反复校正且尚未满足无菌标准。

AI PM 视角：这是具身智能进入高 stakes 物理场景的关键一步。达芬奇手术机器人长期垄断微创外科，核心壁垒不仅是机械臂精度，还包括 20 余年积累的临床数据、FDA/CE 监管路径、医生培训体系与医院采购流程。宇树 G1 以人形形态和通用手术器械完成活体猪胆囊切除，说明**人形机器人可以用“通用硬件 + 软件适配”挑战专用医疗器械的纵向整合模式**。对 PM 来说，这意味着医疗机器人产品化的新路径：不必复制达芬奇的全套专用生态，而是先证明通用机器人在特定术式中的成本优势和可扩展性，再通过监管申报和临床证据补齐合规护城河。 不过，论文也明确指出了两个产品化瓶颈：反复校正和无菌标准不达标。反复校正意味着系统目前的自主性与可靠性还不足以直接进入人体手术；无菌标准不达标则涉及材料、结构、清洁流程等工程细节。PM 在做医疗 AI 产品时，必须区分“技术可行性 demo”和“临床可用产品”之间的鸿沟，并把“可验证的安全性”作为比“惊艳参数”更重要的优先级。

AI Builder 视角：Builder 应关注这次手术背后的系统耦合：人形机器人平台、常规腹腔镜器械、视觉伺服、力反馈与运动规划如何协同。32 分钟完成手术是一个 impressive 的工程集成结果，但“反复校正”暗示当前系统依赖人类监督或在线修正， autonomy 栈尚未闭环。工程团队若借鉴此路线，应优先投资仿真到真实的迁移能力（sim-to-real）、力控安全边界、以及可复用的手术动作原语库。此外，医疗场景对可追溯性与故障模式分析要求极高，Builder 需要尽早引入形式化安全约束和日志审计。

研究型 Builder 视角：真正值得研究的是：为什么选择宇树 G1 这种低成本人形平台，而不是继续优化专用手术臂？答案可能在于“通用机器人 + 任务特定适配”的研究假设——如果通用硬件能通过软件达到接近专用硬件的性能，那么机器人学习、模仿学习、在线校正算法将成为核心创新点。研究者应复现或分析其控制策略、失败案例和校正模式，评估该方法在不同术式上的泛化性。同时，成本仅为达芬奇 5% 这一数字需要拆解：是硬件 BOM 成本、总拥有成本，还是一次性采购成本？这对研究的可比性和产品定价模型至关重要。

可落地的方法论：- **本周**：整理医疗机器人领域“技术 demo → 临床试验 → 监管审批 → 医院采购”的标准路径，识别自家产品所处阶段。 - **本季度**：如果你是具身智能团队，选择 1 个低风险的物理任务（如实验室自动化、康复训练），建立“可验证安全性”指标，而不是只看成功率。 - **长期**：在设计硬件平台时，预留无菌/安全认证接口（可拆洗结构、材料兼容性、紧急制动），避免后期因为合规返工。 ---

3 博科圣地如何利用前沿 AI 技术

2025 至 2026 年对尼日利亚东北部 27 名前博科圣地成员的访谈揭示，该组织在 2024 年系统性利用 ChatGPT、Claude、Gemini、Grok、Meta AI 和 DeepSeek 等前沿 AI 辅助作战与日常运作，AI 应用已通过专门小组和内部培训实现制度化，用途包括袭击策划、武器故障排查及爆炸装置设计。

AI PM 视角：这是目前最具体、最系统化的“前沿 AI 被恐怖组织制度化滥用”的公开证据。对 AI PM 来说，它打破了一个常见幻觉：安全限制对于极端用户场景并非不可绕过。报告中的关键词——“专门小组”“内部培训”“跨国圣战网络传播”“伊斯兰国特工面对面培训”——说明 adversarial users 已经把模型滥用当作一项有组织、可扩散、可迭代的能力来建设。这意味着产品安全设计不能停留在“发布前红队测试”和“免责声明”，而必须进入**持续威胁情报、极端场景红队、社区监测与模型使用审计**的闭环。 更深层的启示是：AI 产品的用户画像分析正在失效。传统 PM 用合规用户、企业用户、消费者来划分需求；但当产品被恶意用户重新包装时，需求分析必须包含 adversarial personas。尤其是搜索、代码、多模态生成、长上下文等能力，天然适合被用于知识转移、武器故障排查和伪装宣传。PM 在定义功能边界时，需要引入“最坏情况用户旅程”方法，把极端 misuse 当作产品需求来管理。

AI Builder 视角：Builder 需要认识到，模型安全不是单一团队的责任，而是贯穿数据、训练、部署、监控、反馈的全栈问题。博科圣地成员能够“绕过部分安全限制”，说明当前 RLHF、系统提示、输出过滤等单一防御手段存在可规模化的绕过模式。工程团队应投资多层次的防御：输入侧异常检测、输出侧结构化限制、使用模式异常监测、长会话上下文审计、以及面向高风险主题的“硬拒绝 + 升级机制”。此外，MCP、插件、代码执行等 Agent 能力会进一步放大 misuse 的攻击面，Builder 在接入这些能力时必须默认采用最小权限和沙盒隔离。

研究型 Builder 视角：这份报告为 AI 安全研究提供了难得的田野数据：27 名前成员的半结构化访谈，揭示的是真实世界中 misuse 的制度化路径，而非实验室里的 jailbreak 比赛。研究者可以从中提炼出几个关键问题：恐怖分子使用 AI 的平均任务复杂度是多少？他们更依赖模型的哪些能力（代码生成、长文本理解、多语言、匿名化）？组织内部如何传播提示词技巧和绕过方法？这些问题的答案，可以直接指导下一代安全评估基准的设计。更重要的是，研究者应推动这类田野研究与模型开发团队的闭环，把真实 adversarial 用例转化为可测量的安全指标。

可落地的方法论：- **本周**：召集产品、安全、法务开一个“极端用户画像”工作坊，针对核心功能列出 5 种最坏情况 misuse 场景。 - **本季度**：建立模型使用异常监测原型，对长代码生成、爆炸物/武器相关查询、多语言匿名化请求等设置分级告警。 - **长期**：把“对抗性鲁棒性”作为模型选型和产品发布的硬性 gate，和安全团队共建持续红队机制，而不是一次性合规检查。 ---

4 百度搭子在成都 AI Day 发布四项更新

百度搭子在成都百度 AI Day 上发布四项更新：个人版升级（浏览器调用、智能路由、多端共享记忆、强化 PPT 生成、新增数字人与报告解读 Skill）、行业首个自媒体专业套件、企业版（团队协作与权限管理），并启动“搭子联盟”，上线三个月日均提问量增长 20 倍。

AI PM 视角：百度搭子的这次更新展示了一个清晰的“个人 → 专业创作者 → 企业 → 生态”四层扩张路径。最值得关注的是“自媒体专业套件”和“搭子联盟”这两个产品信号。前者说明百度不再只是把大模型包装成通用助手，而是**把 AI 能力嵌入一个具体职业（自媒体人）的端到端工作流**：选题、创作、分发、复盘。后者说明百度意识到单一模型能力难以形成壁垒，必须通过联盟把中国联通等生态伙伴拉入自己的服务网络，从而把模型能力转化为平台分发能力。 “日均提问量增长 20 倍”是一个强烈的 PM 信号：当产品从“聊天工具”变成“工作流中的协作节点”时，使用频率会呈现非线性增长。个人版的 Skill（一镜数字人、灵医报告解读）则是在把通用 Agent 拆解为可插拔的垂直能力。对 AI PM 的启示是：未来产品竞争的关键不是模型本身，而是**谁能把模型能力最快、最顺滑地嵌入用户已有的职业工作流，并通过记忆、权限、协作机制形成网络效应**。

AI Builder 视角：Builder 应关注“智能路由”和“多端共享记忆”这两个技术点。智能路由宣称平均任务耗时下降 20%、Token 利用率提升 25%，背后是任务意图识别、模型选择、成本与质量权衡的工程化。多端共享记忆则涉及跨设备状态同步、隐私隔离、长短期记忆分层。对于希望搭建类似 Agent 平台的团队，这两项都是必须跨越的架构门槛。Skill 插件化机制也值得研究：百度如何让第三方 Skill 在统一内存、权限和调用规范下运行？这很可能成为国内版“MCP/Agent Skill”生态的早期形态。

研究型 Builder 视角：从研究角度看，搭子联盟和垂直 Skill 提供了一个观察“模型能力产品化”的窗口。研究者可以追问：智能路由的收益在不同任务类型上是否稳定？20% 耗时降低是否主要来自简单任务被路由到轻量模型？共享记忆是否带来了真正的长程一致性，还是只是历史检索增强？自媒体套件的“选题到复盘”链路中，哪些环节是模型擅长的，哪些仍需人工介入？回答这些问题，可以帮助学术界和工业界更好地定义“Agent 产品化”的评估标准。

可落地的方法论：- **本周**：选择一个目标职业或垂直场景，画出其端到端工作流，标出 3 个 AI 可替代/增强的环节。 - **本季度**：如果你在做 Agent 产品，设计一个“任务路由器”原型：根据意图复杂度、成本预算、响应延迟自动选择模型或工具链。 - **长期**：构建“记忆 + 权限 + Skill”三位一体的 Agent 平台架构，让用户在跨设备、跨团队协作中感受到一致性体验。 ---

5 Cognition 如何信任 Claude Fable 5 通宵工作

Cognition 研究高级副总裁 Silas Alberti 表示，其 AI 软件工程师 Devin 测试了几乎所有 Claude 模型，Claude Fable 5 是首个能信任其通宵运行的模型；在 Cognition 自建的 Frontier Code 基准最难子集上，Fable 5 得分约 30%，而此前 Opus 约 10%，且能连续工作 8 小时并取得实际进展。

AI PM 视角：“通宵工作”是 AI Agent 产品化叙事中的一个质变点。此前的 coding agent 大多是在分钟级或小时级任务中辅助人类；而 Cognition 强调的 8 小时连续自主工作，意味着 Agent 开始具备“异步员工”的属性。这对 PM 的核心启示是：产品定位需要从“助手”升级为“可委托的协作者”，而设计重点也从“单次交互质量”转向“长周期任务一致性、进度可视化和信任修复机制”。 Cognition 提到的几个细节极具产品意义：Fable 5 能正确使用内部调试工具、在混乱上下文中保持清晰思路、主动说明未知信息以重建信任。这说明长程 Agent 的可靠性不仅来自模型能力，还来自**元认知行为**——知道什么时候该确认、什么时候该停下、什么时候该报告进度。PM 在设计类似产品时，应该把“信任协议”作为核心功能：明确的任务边界、定期的 checkpoint、失败时的回滚与解释、以及人类接管接口。

AI Builder 视角：Builder 需要理解“可通宵运行”背后的系统工程。连续 8 小时不偏离目标，意味着上下文管理、工具调用循环、错误恢复、资源限制都必须高度稳定。Cognition 提到的“混乱上下文中保持清晰思路”暗示 Fable 5 在长上下文压缩、目标保持和无关信息过滤上有显著提升。工程团队应优先投资：长上下文状态机、工具调用失败重试策略、沙盒化执行环境、以及可回滚的中间产物版本控制。此外， overnight agent 必须解决“模型在无人监督时如何安全地访问代码库、CI/CD、云平台”等权限问题。

研究型 Builder 视角：从研究角度，Fable 5 的突破提出了一个关键问题：是什么让模型从“10% 到 30%”的同时，还能把有效工作时长扩展到 8 小时？这很可能不只是 scaling 的结果，而是训练目标、推理时计算、工具使用反馈和自我纠错机制共同作用的产物。研究者应关注 Anthropic 在训练 Fable 时是否引入了针对长程一致性的新损失函数或 RL 奖励，以及其内部调试工具调用轨迹如何被用于在线学习。Cognition 的 Frontier Code 基准若未来开源，将成为评估长程 coding agent 的重要资源。

AI PM 视角：“通宵工作”是 AI Agent 产品化叙事中的一个质变点。此前的 coding agent 大多是在分钟级或小时级任务中辅助人类；而 Cognition 强调的 8 小时连续自主工作，意味着 Agent 开始具备“异步员工”的属性。这对 PM 的核心启示是：产品定位需要从“助手”升级为“可委托的协作者”，而设计重点也从“单次交互质量”转向“长周期任务一致性、进度可视化和信任修复机制”。

Cognition 提到的几个细节极具产品意义：Fable 5 能正确使用内部调试工具、在混乱上下文中保持清晰思路、主动说明未知信息以重建信任。这说明长程 Agent 的可靠性不仅来自模型能力，还来自元认知行为——知道什么时候该确认、什么时候该停下、什么时候该报告进度。PM 在设计类似产品时，应该把“信任协议”作为核心功能：明确的任务边界、定期的 checkpoint、失败时的回滚与解释、以及人类接管接口。

AI Builder 视角：Builder 需要理解“可通宵运行”背后的系统工程。连续 8 小时不偏离目标，意味着上下文管理、工具调用循环、错误恢复、资源限制都必须高度稳定。Cognition 提到的“混乱上下文中保持清晰思路”暗示 Fable 5 在长上下文压缩、目标保持和无关信息过滤上有显著提升。工程团队应优先投资：长上下文状态机、工具调用失败重试策略、沙盒化执行环境、以及可回滚的中间产物版本控制。此外， overnight agent 必须解决“模型在无人监督时如何安全地访问代码库、CI/CD、云平台”等权限问题。

研究型 Builder 视角：从研究角度，Fable 5 的突破提出了一个关键问题：是什么让模型从“10% 到 30%”的同时，还能把有效工作时长扩展到 8 小时？这很可能不只是 scaling 的结果，而是训练目标、推理时计算、工具使用反馈和自我纠错机制共同作用的产物。研究者应关注 Anthropic 在训练 Fable 时是否引入了针对长程一致性的新损失函数或 RL 奖励，以及其内部调试工具调用轨迹如何被用于在线学习。Cognition 的 Frontier Code 基准若未来开源，将成为评估长程 coding agent 的重要资源。

方法论
  • 本周：为团队现有 coding agent 或自动化脚本增加“进度 checkpoint + 人类确认”机制，避免无人监督时产生不可控的副作用。
  • 本季度：设计一个“长程任务信任仪表板”，可视化 Agent 的当前步骤、已消耗 token/时间、最近一次人类交互点和置信度。
  • 长期：把“主动说明未知信息”作为 Agent 交互规范，训练或提示模型在不确定时停止并请求澄清，而不是继续猜测。

3 CROSS-CUTTING MODELS
01

框架 1：从“算力军备”到“算力金融化”

今天的多条事件共同指向一个结构性转变：算力不再只是成本中心，而正在成为可出租、可交易、可货币化的战略资产。

  • Meta Compute 直接把过剩或阶段性空闲的 AI 基础设施对外出租，用市场价格覆盖资本支出。
  • DeepSeek-V4 Flash 在 AMD MI355X 上的 RL 训练 说明训练栈开始摆脱单一芯片供应商，进一步增加算力供给端的竞争和议价空间。
  • 小红书 PIPO 和 蚂蚁 SGLang 则从算法和系统层面压缩单位 token 成本，让同样算力产出更多智能。

产品启示：AI 产品经理需要建立“算力资产负债表”思维。一方面，把推理成本拆解到每个用户、每个功能、每个模型调用；另一方面，把算力弹性（云服务、自研芯片、混合部署）纳入产品定价和毛利模型。未来 12-18 个月，能够在“模型能力足够好”的前提下把推理成本压到最低的产品，将获得最大的定价自由度和扩张空间。

02

框架 2：“可通宵 Agent”的信任协议

Cognition 信任 Claude Fable 5 通宵工作，与 Claude Code 应用内浏览器、GitHub Copilot 审查经验共同构成一个主题：长程 Agent 的核心挑战不是能力，而是可预测性、可观测性和可修复性。

  • Fable 5 通过主动说明未知信息、在混乱上下文中保持目标一致性来重建信任。
  • Claude Code 浏览器 扩展了 Agent 的信息边界，但也引入了网页安全和会话持久化的风险。
  • GitHub Copilot 审查 证明，当 Agent 被错误地赋予“通用助手”角色时，即使是好工具也会成本飙升、质量下降。

产品启示：设计长程 Agent 时，必须先定义“信任协议”——任务边界、进度 checkpoint、人类接管点、失败回滚机制和解释性输出。产品体验的核心不再是“模型多聪明”，而是“人类在多远的距离上可以放心地把任务交给它”。建议把 Agent 的“透明度指标”和“干预响应时间”作为和准确率同等重要的产品指标。

03

框架 3：AI 双用途与“极端用户场景”产品治理

Apple 起诉 OpenAI、博科圣地系统性利用前沿 AI、Thinking Machines Lab 强调“延伸人类意志”三组事件，共同把 AI 治理问题推到了产品定义阶段。

  • 商业机密盗窃 说明 AI 竞争正在侵蚀传统的企业边界和知识产权框架。
  • 恐怖组织制度化使用 AI 证明 jailbreak 和红队测试的对抗面远比想象中广泛。
  • Thinking Machines Lab 提出“用户可塑造模型”的愿景，但可定制性越强，滥用和失控的风险也越高。

思考题 1：当 Agent 可以通宵工作，产品该如何定义“完成”与责任边界？

Cognition 已经信任 Claude Fable 5 连续工作 8 小时，这比人类工程师的日常连续工作时长还长。当一个 Agent 在无人监督的情况下修改代码、部署服务、调用工具时，“任务完成”的定义必须从“输出正确”扩展到“过程可审计、结果可回滚、异常可告警”。

  • 产品策略层面： overnight Agent 的 SLA 应该如何设定？是按任务成功率、还是按人类介入频率、抑或是按造成的最大可接受损失来定义？
  • 团队执行层面： 哪些任务类型可以先交给通宵 Agent，哪些必须保留人类在环？如何设计渐进式授权机制？
  • 风险机会层面： 如果 Agent 在夜间造成了生产事故，责任应如何分配给模型提供商、平台方、使用团队和监督者？
